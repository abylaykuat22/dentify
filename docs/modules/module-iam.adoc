|Description
|«Доступы и аккаунты»: аккаунты, членство в клиниках, роли и права, приглашения, журналы, сессии. 
+
Зависит от clinic (`clinic :: api`) и платформы: `platform :: api`, как все модули, и `platform :: identity` — только iam (клиника в сессии, вход, сессии, лимиты входа, чтение журнала). Подписан на события staff (`staff :: events`: `StaffDeactivated` → гасит сессии). Ни один модуль от iam не зависит.
|Base package
|`kz.dentify.iam`
|Bean references
|* `k.d.c.api.ClinicDirectory` (in Моя клиника) -- Клиника контекста и её филиалы — названия для шапки, выбора клиники и филиала (`GET /api/v1/me`, T-IAM-02). Только клиника текущего контекста (`k.d.p.api.TenantContext`): чужую клинику RLS не показывает, списка всех клиник нет. Карточка клиники с реквизитами, адресами и часами филиалов — T-CLN-01, T-CLN-02.
* `k.d.p.identity.AccountSessions` (in Платформа) -- Активные сессии аккаунта (PLT-04): их хранит Spring Session в Valkey с индексом по аккаунту. На этом строятся экран активных сессий и принудительный выход. 
+
Завершённая сессия гаснет сразу и необратимо: следующий запрос с её cookie получает 401 `error.session-expired` с любого устройства, в том числе если в момент завершения шёл её запрос. Так деактивация сотрудника и смена пароля гасят сессии аккаунта быстрее, чем за 5 секунд: iam вызывает `terminateAll(UUID)` или `terminateOthers(UUID, String)`. Эти два гасят и сессии аккаунта со входом до вызова, которых нет в списке, — по времени входа: вход, шедший одновременно и получивший время входа позже вызова, они не гасят. Поэтому iam вызывает их после коммита деактивации или смены пароля, а вход после `k.d.p.identity.AccountSignIn#signIn` перечитывает аккаунт (docs/architecture.md, Активные сессии). 
+
Id сессии в Valkey наружу не отдаётся: это пароль на время сессии. У каждой сессии есть открытый id `k.d.p.identity.AccountSession#id()` — хэш настоящего, по нему интерфейс и завершает сессию.
* `k.d.p.api.PasswordPolicy` (in Платформа) -- Правила пароля (PLT-05): от {@value #MIN_LENGTH} до {@value #MAX_LENGTH} символов, без требований к составу; пароль из списка 10 000 самых частых и совпадающий с телефоном или e-mail аккаунта отклоняется. Сравнение со списком — без учёта регистра. 
+
Проверяют регистрация, приглашение, сброс и смена пароля (модуль iam) до хэширования. Хэш — бином Spring Security `PasswordEncoder`: Argon2id, в БД формат `{argon2`…}. Пароль нигде не логируется и в сообщения ошибок не попадает.
* `k.d.c.api.DemoClinic` (in Моя клиника) -- Вымышленная демо-клиника для локального входа и демо этапа 0: «Dentify Demo» с филиалом «Абая, 150» в Алматы. Бин есть только в профиле `dev`; его вызывает dev-сид модуля iam, который заводит владельца. Идентификаторы постоянные: по ним сид узнаёт, что клиника уже создана, — найти клинику по названию нельзя, RLS показывает только клинику контекста.
* `k.d.p.identity.RateLimits` (in Платформа) -- Лимиты частоты для входа и сброса пароля (PLT-05). Счётчики живут в Valkey и общие для всех экземпляров приложения; логин, e-mail и IP в ключах только хэшем SHA-256. Превышение — `k.d.p.api.TooManyRequestsException`: ответ 429 с `Retry-After`. Общий лимит API на сессию ставит фильтр платформы сам, модулям его вызывать не нужно. 
+
Вход (iam, T-IAM-02):  <pre> rateLimits.checkLogin(login, request.getRemoteAddr());   // до проверки пароля: 429, даже если пароль верный if (!passwordMatches) { boolean locked = rateLimits.recordLoginFailure(login); // + запись в журнал входов, locked — ещё и блокировка throw new UnauthorizedException(...); } rateLimits.resetLogin(login); </pre>  Каждая попытка после `checkLogin` заканчивается `recordLoginFailure` или `resetLogin`, а если пароль так и не проверен (429 предела одновременных хэшей) — `abandonLogin`: проверка заранее занимает место попытки в счётчике логина, чтобы одновременные попытки не прошли её разом. Попытка, которая не закончилась ни одним из них (другое исключение между ними), считается неверной, пока не выйдет из 15-минутного окна. Отказ `checkLogin` журнал входов пишет только при `firstLoginRejection`: отказ ничего не стоит нападающему, а строка журнала — стоит. 
+
Логин и e-mail приводятся к нижнему регистру без крайних пробелов; телефон вызывающий нормализует сам, как хранит.
* `k.d.p.identity.AccountSignIn` (in Платформа) -- Вход и выход в серверной сессии (PLT-04). Пароль, блокировки и журнал входов проверяет вызывающий — вход модуля iam (T-IAM-02); здесь только то, что делает из проверенного аккаунта сессию: <ul> <li>новый id сессии — защита от фиксации: id, известный до входа, после входа недействителен;</li> <li>новый CSRF-токен в cookie `XSRF-TOKEN`, если старый был;</li> <li>аккаунт в контексте Spring Security и в сессии, по нему сессия попадает в индекс аккаунта, см. `k.d.p.identity.AccountSessions`;</li> <li>браузер, IP и время входа — для списка активных сессий;</li> <li>Запомнить: сессия живёт 30 дней от входа, как бы активно ею ни пользовались, cookie постоянная на тот же срок; продлевает срок только новый вход. Без галочки cookie сессионная, до закрытия браузера, а сессия обрывается после 12 часов бездействия и в любом случае через 30 дней от входа. После срока запрос с cookie — 401 `error.session-expired`.</li> </ul> Клиника, выбранная в этой сессии до входа, снимается; клинику нового входа кладёт `k.d.p.identity.TenantSession` после проверки членства. 
+
Вход, шедший одновременно с деактивацией или сменой пароля, `k.d.p.identity.AccountSessions#terminateAll` гасит, только если его время входа не позже вызова. Поэтому вызывающий после `signIn` перечитывает аккаунт новым запросом к БД — статус и версию учётных данных — и, если они изменились с проверенных, выходит (`signOut`) и отвечает 401 (docs/architecture.md, Активные сессии).
* `k.d.p.api.CurrentAccountProvider` (in Платформа) -- Id аккаунта, от имени которого идёт работа. Из него аудит сущностей заполняет `created_by` и `updated_by` (`k.d.p.api.BaseEntity`), им пользуются модули, которым нужен вошедший аккаунт. Реализация — платформа по контексту Spring Security (T-PLT-04): имя вошедшего — id аккаунта, его ставит `identity.AccountSignIn`. Бин один: вторая реализация сделала бы аудит пустым.
* `k.d.p.identity.AuditJournal` (in Платформа) -- Чтение журнала действий клиники контекста (PLT-09) для модуля iam: экран журнала и его выгрузка. Всегда только клиника контекста, без неё — `k.d.p.api.MissingTenantContextException`. Право на чтение журнала проверяет эндпоинт; ИИН, телефон и e-mail без права `k.d.p.api.Permissions#PATIENT_PHONES` отдаются маской.
